# illoominus-ds

Production data-science batch job.

## Project Structure

```text
.
├── Dockerfile
├── docker-compose.yaml
├── scripts/
│   ├── main.R                 # orchestration: CLI, loop, summary
│   ├── duckdb/                # DuckDB shell and shared data-lake SQL (R reads from here too)
│   │   ├── data_lake_bootstrap.sql.template
│   │   ├── data_lake_schema.sql.template
│   │   └── duckdb_shell_entrypoint.sh
│   └── R/
│       ├── ds_utils.R
│       ├── data_lake.R
│       └── model.R
└── data/
    ├── inputs/
    └── outputs/
```

## Usage

### Option 1: Docker with local output (default)

```bash
docker compose build
docker compose run --rm illoominus-ds
```

By default, outputs are written to `data/outputs/{timestamp}/` and mirrored to `data/outputs/latest/`.

### Option 2: Docker with S3 output

```bash
docker compose run --rm illoominus-ds \
  Rscript /app/scripts/main.R \
  --output-type=s3 \
  --output-path=s3://illoominus-data-engineering/illoominus-ds
```

### Targeted company runs (optional)

Run one company:

```bash
docker compose run --rm illoominus-ds \
  Rscript /app/scripts/main.R \
  --company-id=123
```

Limit to first N companies:

```bash
docker compose run --rm illoominus-ds \
  Rscript /app/scripts/main.R \
  --company-limit=5
```

Run a specific list from file (one ID per line):

```bash
docker compose run --rm illoominus-ds \
  Rscript /app/scripts/main.R \
  --company-id-file=data/inputs/company_ids.txt
```

## AWS Credentials

The compose configuration mounts host credentials into the container:

- `~/.aws:/root/.aws:ro`
- `AWS_SDK_LOAD_CONFIG=1`

Validate credentials before running:

```bash
aws sts get-caller-identity
```

## DuckDB shell (interactive, read-only)

An interactive DuckDB CLI session is available for querying the S3 data lake. The session is **read-only** (no writes to the data lake). It uses the same AWS credentials and data-lake configuration as the main job.

```bash
docker compose run --rm duckdb-shell
```

On startup, the shell runs the same SQL as the R data-lake session: `scripts/duckdb/data_lake_bootstrap.sql.template` (extensions, secret) and `scripts/duckdb/data_lake_schema.sql.template` (views and per-company macros such as `employees(company_id)`, `departments(company_id)`, `job_histories(company_id)`). Add or edit views and macros in the schema file so both R and the CLI stay in sync. Override URL or region at runtime:

```bash
docker compose run --rm -e DATA_LAKE_BASE_URL=s3://my-bucket/path -e DATA_LAKE_S3_REGION=us-west-2 duckdb-shell
```

The init script uses `DATA_LAKE_BASE_URL` and `DATA_LAKE_S3_REGION` (defaults: `s3://illoominus-data-engineering/data-lake`, `us-east-1`). The R data-lake connection used by the main job is also read-only.

## Data Lake Configuration

Data lake SQL is split into two shared templates under `scripts/duckdb/`: `data_lake_bootstrap.sql.template` (LOAD extensions, CREATE SECRET) and `data_lake_schema.sql.template` (views and CREATE MACRO for per-company tables). Both the R job and the DuckDB shell read these files (with runtime substitution of `__BASE_URL__` and `__S3_REGION__`), so the schema stays consistent.

The data lake URL is controlled by environment variable with a default fallback:

- `DATA_LAKE_BASE_URL` (optional; if unset, default from `scripts/R/data_lake.R` is used)
- `DATA_LAKE_S3_REGION` (optional; defaults to `us-east-1`)

Examples:

```bash
docker compose run --rm illoominus-ds \
  env DATA_LAKE_BASE_URL=s3://my-data-lake/root \
  Rscript /app/scripts/main.R
```
